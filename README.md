# КБЖВ

Персональний PWA-застосунок для обліку калорійності, БЖВ, цукрів, солі, клітковини, продуктів, денних підсумків та історії.

**Основний сайт:** https://anthonybatyk.github.io/kbjv-released-program-version-7495/

## Основні можливості

- КБЖВ Блоки — власна база продуктів, редагування, сортування, відділи, власні відділи та швидкі ваги.
- КБЖВ Калькулятор — ручне складання прийому їжі/дня, розділи та власні швидкі КБЖВ.
- КБЖВ Архів — денна історія, дата, текст, склад, коментар та статистика.
- Консоль — Повернути, Оновити, Вийти, Очистити та Видалити акаунт.
- Профіль — фото, відображуване ім’я, ПІБ, дата народження, поточна вага та зріст.
- Export / Import — резервне копіювання всіх даних або окремих частин.
- Авторизація — централізований вхід через Cloudflare Worker + D1.
- Admin — список користувачів, ролі, дата реєстрації, останній вхід, історія входів та серверна історія активності.
- PWA — сайт можна встановити на головний екран телефона і використовувати як окрему програму.

## Архітектура

### Front-end

Front-end працює як статичний PWA на GitHub Pages.

Основні файли:

- `index.html`
- `style.css`
- `script.js`
- `manifest.webmanifest`
- `sw.js`
- `icon.png`
- `icon-192.png`
- `icon-512.png`

### Авторизація і Admin

Backend авторизації працює через Cloudflare Worker:

`https://kbjv-auth-api.anthonybatyk.workers.dev`

Cloudflare D1 зберігає:

- облікові записи;
- хеші паролів;
- ролі `member` / `admin`;
- серверні сесії;
- час реєстрації;
- останній вхід;
- історію входів.

Паролі у відкритому вигляді не зберігаються.

### Дані КБЖВ

Продукти, калькулятор, архів, статистика, профіль, власні відділи, швидкі ваги, швидкі КБЖВ та інші користувацькі дані зберігаються **локально на пристрої користувача** у `localStorage`.

Кожний акаунт має окремий namespace локальних даних, тому два акаунти на одному пристрої не повинні змішувати свої дані.

**Важливо:** КБЖВ-дані зараз не синхронізуються автоматично між різними телефонами/комп’ютерами. Для перенесення даних використовується Export / Import.

## Офлайн-режим

Застосунок підтримує офлайн-роботу.

Після хоча б одного успішного онлайн-запуску Service Worker кешує оболонку PWA. Після цього встановлений застосунок може відкриватися без інтернету.

Офлайн можна:

- відкривати КБЖВ Блоки;
- додавати та редагувати продукти;
- користуватися КБЖВ Калькулятором;
- додавати історію;
- змінювати профіль;
- користуватися локальною статистикою;
- виконувати Export локальних даних;
- зберігати всі зміни на цьому пристрої.

Коли інтернет повертається, сайт знову може звертатися до Cloudflare для перевірки сесії та Admin-функцій.

### Важливе обмеження офлайн-входу

Для надійного повторного відкриття PWA офлайн потрібно мати вже збережену авторизовану сесію. Найнадійніший варіант — при вході використовувати **Remember me**.

Без інтернету неможливо:

- створити новий акаунт;
- виконати новий серверний login, якщо локальної сесії вже немає;
- завантажити актуальний список користувачів Admin;
- завантажити серверну історію входів;
- виконати logout на сервері до відновлення мережі.

Локальні КБЖВ-дані не потребують Cloudflare для кожного запису і не зникають через тимчасову відсутність інтернету.

## Сесії

Поточна серверна логіка:

- `Remember me` — сесія до 30 днів;
- без `Remember me` — серверна сесія до 12 годин;
- при звичайному запуску сайт перевіряє активну сесію через `/auth/me`;
- якщо мережі немає, але збережена локальна сесія та дані користувача є, PWA може перейти в офлайн-режим.

У застосунку немає окремого правила на кшталт «20 входів на день» або «100 входів на день».

## Cloudflare Free — актуальні обмеження

Станом на **4 жовтня 2026 року**.

### Workers Free

- до **100 000 Worker-запитів на день** на акаунт;
- ліміт скидається о `00:00 UTC`;
- CPU time — **10 ms на один запит**;
- пам’ять — **128 MB**;
- до **50 зовнішніх subrequests** на один Worker invocation;
- до **1 000 subrequests до Cloudflare services** на один invocation.

Офіційне джерело:
https://developers.cloudflare.com/workers/platform/limits/

### D1 Free

- **5 000 000 rows read / день**;
- **100 000 rows written / день**;
- **5 GB** загального D1 storage на Free account;
- максимум **500 MB на одну D1 database**;
- до **10 D1 databases** на Free account;
- Free-ліміти читання/запису скидаються щодня о `00:00 UTC`.

Офіційні джерела:
https://developers.cloudflare.com/d1/platform/pricing/
https://developers.cloudflare.com/d1/platform/limits/

Починаючи з 1 вересня 2026 року Cloudflare реально блокує D1 queries після перевищення денного Free-ліміту rows read або rows written до наступного скидання ліміту. Уже збережені дані при цьому не видаляються.

Джерело:
https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/

## Чи можна входити 100 разів на день?

Так.

Сам застосунок не встановлює такого обмеження. Один login створює лише невелику кількість Worker/D1 операцій. Навіть 100 входів на день — дуже далеко від **100 000 Worker requests/day** і від D1 Free-лімітів для такого невеликого проєкту.

Фактичне споживання D1 рахується не просто «за входами», а за кількістю рядків, які SQL-запити реально прочитали або записали.

## Кількість користувачів

У коді немає фіксованого ліміту на 10, 20, 50 або 100 зареєстрованих користувачів.

Практична межа Free-режиму визначається загальним навантаженням усіх користувачів на:

- Workers requests;
- D1 rows read;
- D1 rows written;
- D1 storage.

Для десятків активних користувачів на день поточна архітектура має дуже великий запас, оскільки звичайні КБЖВ-операції виконуються локально і не створюють запит у D1 при кожному додаванні продукту чи калорій.

## Що відбувається при перевищенні Cloudflare Free-ліміту

Якщо вичерпано Workers Free request limit, backend тимчасово перестане нормально відповідати до скидання денного ліміту.

Якщо вичерпано D1 rows read / rows written, D1 queries тимчасово повертають помилки до `00:00 UTC`.

При цьому:

- локальні КБЖВ-дані на телефоні не видаляються;
- встановлений PWA може продовжувати локальну офлайн-роботу, якщо вже є збережена сесія;
- після відновлення доступу до backend авторизаційні/Admin-функції знову працюватимуть.

## Зберігання та видалення даних

Сайт не повинен самостійно видаляти користувацькі КБЖВ-дані.

Видалення виконується лише через явну дію користувача, наприклад:

- видалення конкретного продукту;
- видалення запису історії;
- видалення відділу;
- `Clear` у Консолі.

`Вийти` виходить з акаунта, але не очищає КБЖВ-дані цього акаунта.

`Оновити` оновлює PWA та повертає в КБЖВ Блоки без logout.

`Видалити акаунт` виконує незворотне серверне видалення акаунта через `DELETE /auth/account`, після чого локальні дані цього акаунта на поточному пристрої також стираються. Для цієї кнопки потрібна backend-версія Worker з підтримкою цього endpoint.

## Резервні копії

Рекомендовано періодично використовувати Export.

Повний Export може містити:

- продукти;
- швидкі ваги;
- архів;
- коментарі до історії;
- денну ціль;
- профіль;
- фото профілю;
- власні/видалені відділи та їх порядок;
- власні швидкі КБЖВ;
- інші дані, що входять у поточний формат резервної копії.

Admin-дані та серверні облікові записи в цей Export не входять — вони зберігаються в Cloudflare D1.

## Розгортання нової версії

1. Розпакувати ZIP релізу.
2. Завантажити окремі файли в корінь GitHub repository.
3. Не завантажувати ZIP замість файлів — GitHub Pages сам ZIP не розпаковує.
4. Дочекатися GitHub Pages deployment.
5. `sw.js` має новий `CACHE_NAME` у кожному релізі, щоб PWA отримав оновлені файли.

## Безпека

- `ADMIN_ACCESS_CODE` зберігається тільки як Cloudflare Worker secret.
- У front-end не повинно бути admin access code.
- Паролі не зберігаються plaintext.
- Admin UI не є єдиним захистом: Admin endpoints також перевіряють роль на backend.
- Cross-origin Cloudflare API responses не кешуються Service Worker.

## Поточна схема

Front-end / PWA:
`GitHub Pages → браузер / встановлений PWA → localStorage`

Авторизація:
`PWA → Cloudflare Worker → D1`

При звичайній роботі з КБЖВ:
`PWA → localStorage`

Тобто база D1 не отримує запит щоразу, коли користувач додає 100 г продукту, редагує калькулятор чи відкриває локальний архів.

## Видалення акаунта

Кнопка **Видалити акаунт** знаходиться в Консолі.

Перед видаленням:

1. показується попередження про незворотність;
2. потрібно вручну ввести логін акаунта;
3. PWA викликає `DELETE /auth/account` з поточною Bearer-сесією;
4. Worker видаляє серверні сесії, історію входів і сам запис користувача з D1;
5. лише після успішної відповіді сервера локальні дані цього акаунта на поточному пристрої стираються.

Якщо інтернету немає або backend повернув помилку, акаунт не видаляється.

## Admin-аудит

Починаючи з v57, Worker підтримує окрему серверну таблицю `user_audit_events`.

Вона показує в Admin тільки важливі події акаунта:

- створення акаунта;
- кожний фактичний вхід через форму входу;
- вихід з акаунта;
- очищення сайту;
- видалення акаунта.

Звичайні дії всередині сайту — відкриття вкладок, редагування продуктів, робота з калькулятором тощо — залишаються лише в локальній Консолі користувача і в Admin не показуються.

Події аудиту не мають зовнішнього ключа на `users`, тому історія не зникає після видалення акаунта. Для кожної події зберігається snapshot логіна та ID користувача.

Якщо користувач виконує дії офлайн, PWA тримає невелику локальну чергу і намагається передати її в аудит після повернення інтернету.

Паролі, токени авторизації та admin access code в аудит не записуються.

Важливо: аудит починає накопичувати події лише після розгортання Worker v3. Акаунти, які були повністю видалені раніше, автоматично відновити в новій історії неможливо.
