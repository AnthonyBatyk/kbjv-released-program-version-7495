# КБЖВ

Персональний PWA-застосунок для обліку калорійності, БЖВ, цукрів, солі, клітковини, продуктів, денних підсумків та історії.

**Основний сайт:** https://anthonybatyk.github.io/kbjv-released-program-version-7495/

## Основні можливості

- КБЖВ Блоки — власна база продуктів, редагування, сортування, відділи, власні відділи та швидкі ваги.
- КБЖВ Калькулятор — ручне складання прийому їжі/дня, розділи та власні швидкі КБЖВ.
- КБЖВ Архів — денна історія, дата, текст, склад, коментар та статистика.
- Консоль — Повернути, Оновити, Вийти, Очистити та Видалити акаунт.
- Профіль — фото, відображуване ім’я, ПІБ, дата народження, поточна вага та зріст.
- Експорт / Імпорт — повна резервна копія локальних даних або перенесення окремих частин.
- Авторизація — централізований вхід через Cloudflare Worker + D1.
- Адмін-панель — список користувачів, ролі, реальні відвідування, входи через пароль, основні події, повна історія активності та read-only знімок поточного стану користувача.
- PWA — сайт можна встановити на головний екран телефона і використовувати як окрему програму.

## Архітектура

### Front-end

Front-end працює як статичний PWA на GitHub Pages.

Основні файли:

- `index.html`
- `style.css`
- `script.js`
- `manifest.webmanifest`
- `sw.js`
- `icon.png`
- `icon-192.png`
- `icon-512.png`

### Авторизація й адмін-панель

Backend авторизації працює через Cloudflare Worker:

`https://kbjv-auth-api.anthonybatyk.workers.dev`

Cloudflare D1 зберігає:

- облікові записи;
- хеші паролів;
- ролі `member` / `admin`;
- серверні сесії;
- час реєстрації;
- останній вхід через логін і пароль;
- останнє фактичне відвідування сайту;
- історію входів;
- серверний журнал дій;
- read-only знімок поточного стану сайту користувача для «Повної інформації».

Паролі у відкритому вигляді не зберігаються.

### Дані КБЖВ

Продукти, калькулятор, архів, статистика, профіль, власні відділи, швидкі ваги, швидкі КБЖВ та інші користувацькі дані зберігаються **локально на пристрої користувача** у `localStorage`.

Кожний акаунт має окремий namespace локальних даних, тому два акаунти на одному пристрої не повинні змішувати свої дані.

**Важливо:** основне сховище КБЖВ-даних залишається локальним. Worker отримує read-only знімок стану для адмін-перегляду, але цей механізм не підміняє локальні дані та не використовується для автоматичного перенесення між пристроями. Для перенесення й відновлення використовується Експорт / Імпорт.

## Офлайн-режим

Застосунок підтримує офлайн-роботу.

Після хоча б одного успішного онлайн-запуску Service Worker кешує оболонку PWA. Після цього встановлений застосунок може відкриватися без інтернету.

Офлайн можна:

- відкривати КБЖВ Блоки;
- додавати та редагувати продукти;
- користуватися КБЖВ Калькулятором;
- додавати історію;
- змінювати профіль;
- користуватися локальною статистикою;
- виконувати експорт локальних даних;
- зберігати всі зміни на цьому пристрої.

Коли інтернет повертається, сайт знову може звертатися до Cloudflare для перевірки сесії, журналу активності та адмін-функцій.

### Важливе обмеження офлайн-входу

Для надійного повторного відкриття PWA офлайн потрібно мати вже збережену авторизовану сесію. Найнадійніший варіант — при вході використовувати **«Запам’ятати мене»**.

Без інтернету неможливо:

- створити новий акаунт;
- виконати новий серверний вхід, якщо локальної сесії вже немає;
- завантажити актуальний список користувачів адмін-панелі;
- завантажити серверну історію входів і дій;
- синхронізувати read-only знімок стану для адмін-панелі;
- виконати серверний вихід до відновлення мережі.

Локальні КБЖВ-дані не потребують Cloudflare для кожного запису і не зникають через тимчасову відсутність інтернету.

## Сесії

Поточна серверна логіка:

- «Запам’ятати мене» — сесія до 30 днів;
- без «Запам’ятати мене» — серверна сесія до 12 годин;
- при звичайному запуску сайт перевіряє активну сесію через `/auth/me`;
- якщо мережі немає, але збережена локальна сесія та дані користувача є, PWA може перейти в офлайн-режим.

У застосунку немає окремого правила на кшталт «20 входів на день» або «100 входів на день».

Станом на **4 жовтня 2026 року**.

Офіційні джерела:
https://developers.cloudflare.com/d1/platform/pricing/

Джерело:
https://developers.cloudflare.com/changelog/post/2026-09-01-d1-free-tier-limit-enforcement/

## Чи можна входити 100 разів на день?

Так.

Сам застосунок не встановлює такого обмеження. Один вхід створює лише невелику кількість Worker/D1 операцій. Окремо v60 синхронізує журнал активності та змінений read-only стан користувача, тому фактичне навантаження залежить не лише від кількості входів, а й від активності на сайті.

Фактичне споживання D1 рахується не просто «за входами», а за кількістю рядків, які SQL-запити реально прочитали або записали.

## Кількість користувачів

У коді немає фіксованого ліміту на 10, 20, 50 або 100 зареєстрованих користувачів.

Практична межа Free-режиму визначається загальним навантаженням усіх користувачів на:

- Workers requests;
- D1 rows read;
- D1 rows written;
- D1 storage.

Звичайні КБЖВ-операції виконуються локально, але v60 додатково надсилає серверний журнал дій і періодично оновлює read-only знімок стану. Тому запас Free-режиму треба оцінювати за реальною кількістю Worker/D1 операцій, а не лише за кількістю зареєстрованих користувачів.

## Що відбувається при перевищенні Cloudflare Free-ліміту

Якщо вичерпано Workers Free request limit, backend тимчасово перестане нормально відповідати до скидання денного ліміту.

Якщо вичерпано D1 rows read / rows written, D1 queries тимчасово повертають помилки до `00:00 UTC`.

При цьому:

- локальні КБЖВ-дані на телефоні не видаляються;
- встановлений PWA може продовжувати локальну офлайн-роботу, якщо вже є збережена сесія;
- після відновлення доступу до серверної частини авторизаційні та адмін-функції знову працюватимуть.

## Зберігання та видалення даних

Сайт не повинен самостійно видаляти користувацькі КБЖВ-дані.

Видалення виконується лише через явну дію користувача, наприклад:

- видалення конкретного продукту;
- видалення запису історії;
- видалення відділу;
- `Очистити` у Консолі.

`Вийти` виходить з акаунта, але не очищає КБЖВ-дані цього акаунта.

`Оновити` оновлює PWA та повертає в КБЖВ Блоки без виходу з акаунта.

`Видалити акаунт` виконує незворотне серверне видалення акаунта через `DELETE /auth/account`, після чого локальні дані цього акаунта на поточному пристрої також стираються. Для цієї кнопки потрібна backend-версія Worker з підтримкою цього endpoint.

## Резервні копії

Рекомендовано періодично використовувати експорт.

Повний експорт v60 містить:

- продукти;
- швидкі ваги;
- поточний калькулятор і його чернетку;
- архів;
- коментарі до історії;
- денну ціль;
- профіль;
- фото профілю;
- власні/видалені відділи та їх порядок;
- власні швидкі КБЖВ;
- режим сортування, активну вкладку, налаштування відділів і статистики;
- локальну консоль дій.

Формат повної резервної копії: `kbjv-full-backup-v2`. Імпорт зберігає сумісність зі старішими JSON-файлами, якщо вони містять підтримувані поля.

Дані серверної адмін-історії, паролі, сесії та самі облікові записи в локальний експорт не входять — вони зберігаються в Cloudflare D1.

## Зміни v60

- пошук у КБЖВ-блоках працює саме за назвою продукту; відділ чи опис більше не піднімає нерелевантні результати;
- повна резервна копія відновлює продукти, калькулятор, чернетку, архів, денну ціль, профіль, швидкі значення, налаштування й локальну консоль;
- останнє відвідування відокремлено від входу через логін і пароль;
- усі дії журналюються сервером із часом до секунди; офлайн-події ставляться в локальну чергу й надсилаються після повернення мережі;
- «Повна інформація» показує історію дій і останній синхронізований read-only стан користувача;
- тільки головний адміністратор може надавати або знімати адмін-права;
- звичайна реєстрація більше не пропонує код адмін-доступу;
- оновлений Service Worker використовує cache `kbjv-pwa-v60`;
- виправлено нижню safe-area смугу у модальних вікнах PWA.

## Розгортання нової версії

1. Спочатку замінити код Cloudflare Worker на `kbjv_worker_v60.js` і виконати Deploy. Окрему ручну D1-міграцію виконувати не потрібно: Worker сам додає потрібні таблиці/колонки при першому запиті.
2. Рекомендовано задати Worker variable `OWNER_USERNAME` з точним логіном головного адміністратора. Якщо зараз у базі лише один `admin`, v60 і без цієї змінної визначить його як власника.
3. Розпакувати ZIP релізу.
4. Завантажити окремі PWA-файли в корінь GitHub repository.
5. Не завантажувати ZIP замість файлів — GitHub Pages сам ZIP не розпаковує.
6. Дочекатися GitHub Pages deployment.
7. `sw.js` має `CACHE_NAME = "kbjv-pwa-v60"`, тому після оновлення PWA підхопить нову оболонку без очищення `localStorage`.

## Безпека

- Нові користувачі реєструються як `member`; у звичайному інтерфейсі немає поля для отримання адмін-прав кодом.
- Лише головний адміністратор може через серверний `PATCH /admin/users/:id/role` надати або зняти роль `admin`.
- Звичайні адміністратори мають лише read-only доступ до адмін-даних і не можуть змінювати ролі.
- Для однозначної фіксації головного адміністратора рекомендовано задати Worker variable `OWNER_USERNAME` з точним логіном головного адміністратора. Якщо змінної немає, Worker використовує найстаріший наявний `admin`-акаунт.
- `ADMIN_ACCESS_CODE` залишається лише аварійним bootstrap-механізмом Worker на випадок порожньої бази без жодного адміністратора; фронтенд його не використовує.
- Паролі не зберігаються у відкритому вигляді.
- Інтерфейс адмін-панелі не є єдиним захистом: серверні маршрути також перевіряють роль і статус головного адміністратора.
- Відповіді Cloudflare API з іншого домену не кешуються Service Worker.

## Поточна схема

Інтерфейс / PWA:
`GitHub Pages → браузер / встановлений PWA → localStorage`

Авторизація, аудит і read-only стан для адмін-панелі:
`PWA → Cloudflare Worker → D1`

Основні КБЖВ-дані продовжують зберігатися локально. Кожна журналювана дія надсилається в серверний аудит, а коли фактичний локальний стан змінився, PWA із затримкою оновлює один read-only знімок у D1. Якщо мережі немає, журнал дій накопичується локально до повернення з’єднання, а стан синхронізується при наступній можливості.

## Видалення акаунта

Кнопка **Видалити акаунт** знаходиться в Консолі.

Перед видаленням:

1. показується попередження про незворотність;
2. потрібно вручну ввести логін акаунта;
3. PWA викликає `DELETE /auth/account` з поточною Bearer-сесією;
4. Worker видаляє серверні сесії, історію входів і сам запис користувача з D1;
5. лише після успішної відповіді сервера локальні дані цього акаунта на поточному пристрої стираються.

Якщо інтернету немає або backend повернув помилку, акаунт не видаляється.

## Адмін-аудит і «Повна інформація»

У v60 Worker зберігає `user_audit_events` і `user_state_snapshots`.

Основна адмінка показує коротку інформацію: реєстрацію, останнє фактичне відвідування, останній вхід через логін і пароль, кількість таких входів та останню критичну дію на кшталт виходу або очищення сайту.

«Повна інформація» показує:

- останній синхронізований read-only стан профілю, денної цілі, КБЖВ-блоків, калькулятора, чернетки, архіву та локальних налаштувань;
- усі серверно отримані дії користувача з датою й часом до секунди;
- додаткові метадані дій, якщо вони були передані клієнтом.

Фото профілю як base64-контент у state snapshot не копіюється; сервер зберігає лише ознаку, що фото встановлено, а зміна/видалення фото залишається в аудиті. Паролі, токени авторизації та секрети Worker в аудит і state snapshot не записуються.

Історія аудиту не має зовнішнього ключа на `users`, тому подія видалення акаунта може залишитися в аудиті після видалення самого користувача. Поточний state snapshot при видаленні акаунта видаляється.

Історія не може заднім числом відтворити дії, зроблені до розгортання цієї логіки. Поточний state snapshot з’явиться після того, як користувач відкриє v60 з інтернетом.
